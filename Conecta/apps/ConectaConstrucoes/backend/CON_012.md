# CON_012 — Categorias e especialidades

Implementação em camadas: Domain contém as entidades; Application contém DTOs, validações, serviço e contrato de repositório; Infrastructure implementa EF Core/Npgsql; API contém os endpoints, autenticação e documentação. Application não depende de Infrastructure.

## Configuração local

Pré-requisitos: .NET SDK 10, PostgreSQL 16, Docker para o banco local. Execute os comandos abaixo na pasta `Conecta/apps/ConectaConstrucoes/backend`.

Não há senha nem chave JWT nos arquivos versionados. Configure as seguintes variáveis na sessão PowerShell (substitua os valores entre `<...>`):

```powershell
$env:ConnectionStrings__Conecta = 'Host=localhost;Port=5432;Database=monorepo_db;Username=admin;Password=<senha-local>'
$env:Jwt__Issuer = '<emissor-acordado>'
$env:Jwt__Audience = '<audiencia-acordada>'
$env:Jwt__SigningKey = '<segredo-HS256-de-pelo-menos-32-bytes>'
$env:ASPNETCORE_ENVIRONMENT = 'Development'
```

Alternativa: `dotnet user-secrets set 'ConnectionStrings:Conecta' '<conexao>' --project Conecta.API`, e equivalentes para `Jwt:Issuer`, `Jwt:Audience` e `Jwt:SigningKey`. A API falha na inicialização se qualquer configuração obrigatória estiver ausente ou a chave for curta. A fábrica de design-time lê conexão das variáveis/user-secrets e dispensa JWT para migrations.

```powershell
dotnet tool restore
dotnet restore Conecta.slnx
dotnet build Conecta.slnx --no-restore
dotnet ef migrations script --project Conecta.Infrastructure --startup-project Conecta.API
dotnet ef database update --project Conecta.Infrastructure --startup-project Conecta.API
dotnet run --project Conecta.API --no-launch-profile --urls http://localhost:5080
```

Swagger em desenvolvimento: `http://localhost:5080/swagger`. Documento Swagger: `/swagger/v1/swagger.json`; documento nativo ASP.NET: `/openapi/v1.json`. Clique em Authorize e informe somente o token; a interface adiciona Bearer. Rotas públicas dispensam autenticação. Em produção a interface e os documentos não são publicados; exponha a API por HTTPS no ambiente de hospedagem.

## Banco e inicialização

A referência deste ticket é `objs/schema.sql`, conforme solicitado: `prestadores.usuario_id` referencia `usuarios.id`, e `prestador_categorias.prestador_id` referencia `prestadores.usuario_id`. `objs/create.sql` representa um desenho diferente: prestador singular, usuários sem perfil direto, roles/usuario_roles, ADMIN_MASTER, enums e outros módulos. Não executar ambos os scripts, nem misturar qualquer deles com esta migration no mesmo schema.

Em banco vazio, a migration `InicialCategoriasESuporte` cria apenas as quatro tabelas necessárias: usuarios, prestadores, categorias e prestador_categorias. Usuarios preserva os campos de suporte de schema.sql; prestadores preserva seus campos e a chave usuario_id. Não cria usuários ou prestadores fictícios, nem fornece cadastro/login. As demais tabelas do SQL ficam para seus respectivos módulos. As migrations e o snapshot são a fonte operacional desse conjunto de tabelas; o SQL gerado ao lado da migration serve para revisão, e não deve ser aplicado novamente após `database update`.

Diferenças deliberadas frente a schema.sql: colunas ativo/criado_em/atualizado_em e adicionado_em adicionadas pelo ticket; timestamps usam `timestamptz` e valores UTC; IDs identity equivalentes ao SERIAL; descrição limitada a 5000 caracteres; plano/status possuem defaults obrigatórios; FKs explicitamente RESTRICT, sem exclusão de dados relacionados. Índice único `uq_categorias_slug`, check de formato do slug e PK composta preservam integridade no PostgreSQL. Não há migrations automáticas na inicialização da API.

Se já houver tabelas criadas pelos scripts, não rode esta migration inicial cegamente. Faça conciliação de esquema e baseline do histórico com a equipe, preservando os dados, antes de aplicar mudanças. Não usar EnsureCreated junto com migrations.

No ambiente verificado em 04/10/2026, um PostgreSQL nativo do Windows ocupava a porta 5432. O container Docker declarava a mesma publicação, porém as conexões do host chegavam ao serviço nativo. Para verificar exclusivamente monorepo-postgres, foi criado um proxy temporário na porta 15432 e na rede já existente:

```powershell
docker run --rm -d --name con012-pg-proxy --network conecta_monorepo-network -p 127.0.0.1:15432:15432 node:20-alpine node -e "const net=require('net');net.createServer(c=>{const s=net.connect(5432,'monorepo-postgres');c.pipe(s).pipe(c);s.on('error',()=>c.destroy());c.on('error',()=>s.destroy());c.on('close',()=>s.destroy());}).listen(15432,'0.0.0.0');"
# Configure Host=127.0.0.1;Port=15432 na mesma conexão, preservando banco/usuário/senha.
# Após parar a API e terminar as verificações:
docker stop con012-pg-proxy
```

Isso não muda o banco, a senha ou o serviço nativo. Se a porta 5432 estiver livre e apontar corretamente ao container, o proxy é desnecessário. O proxy utilizado nesta entrega é removido ao final das verificações.

## JWT e integração pendente

Autenticacao.API ainda é o template WeatherForecast e não possui emissor ou contrato de claims implementado. Este módulo define o contrato mínimo a ser integrado pela equipe, sem criar login:

- Algoritmo HS256, segredo externo compartilhado com o emissor (mínimo 32 bytes).
- `iss` e `aud` devem corresponder exatamente à configuração; assinatura, issuer, audience, expiração e algoritmo são validados.
- `exp` obrigatório; tolerância de relógio de 30 segundos.
- Exatamente um `sub`, inteiro positivo, representando `usuarios.id` e `prestadores.usuario_id`.
- Claim `role` com valores exatos `ADMIN` ou `PRESTADOR`; múltiplos papéis podem ser emitidos como múltiplas claims. O mapeamento automático de claims está desabilitado.
- ADMIN_MASTER de create.sql não é aceito automaticamente como ADMIN. A equipe deverá acordar a tradução no emissor ou migrar o contrato explicitamente.

Somente tokens assinados e validados fornecem identidade e permissões. Headers X-User-Id/X-Role não são usados. Nenhuma rota aceita prestadorId para escolher o proprietário. A existência do prestador é verificada no banco; token PRESTADOR sem registro correspondente retorna 404. Cadastro dos usuários/prestadores reais e emissão de tokens continuam a cargo da autenticação e dos respectivos módulos.

Referências: [validação JWT do ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0) e [Swashbuckle 10.2.3](https://www.nuget.org/packages/Swashbuckle.AspNetCore/10.2.3), compatível com Microsoft.OpenApi 2.7.5.

## Endpoints

| Método | Rota | Permissão | Sucesso |
|---|---|---|---|
| GET | /api/categorias | Público | 200, somente ativas |
| GET | /api/categorias/{slug} | Público | 200, ativa; 404 caso ausente/inativa |
| GET | /api/admin/categorias | ADMIN | 200, inclui inativas |
| POST | /api/categorias | ADMIN | 201, Location e DTO |
| PUT | /api/categorias/{id} | ADMIN | 200, DTO atualizado |
| PATCH | /api/categorias/{id}/ativo | ADMIN | 200, DTO atualizado |
| GET | /api/prestadores/me/categorias | PRESTADOR | 200, inclui próprias inativas |
| POST | /api/prestadores/me/categorias/{categoriaId} | PRESTADOR | 204 |
| DELETE | /api/prestadores/me/categorias/{categoriaId} | PRESTADOR | 204 |

400 para entrada inválida; 401 para token ausente/inválido; 403 para papel inadequado; 404 para categoria/prestador ausente; 409 para slug duplicado ou associação a categoria inativa. Erros de negócio retornam ProblemDetails sem detalhes internos do banco. Erros inesperados retornam mensagem genérica 500. IDs negativos/inexistentes não selecionam outro usuário.

Nome obrigatório, máximo 100; slug obrigatório, máximo 100; descrição opcional até 5000; ícone opcional até 255 e URL absoluta HTTP/HTTPS. Slug é aparado, convertido para minúsculas, sem acentos, e espaços tornam-se hífens; após normalização aceita `[a-z0-9]+(-[a-z0-9]+)*`. Nome e demais dados não são alterados na mudança de ativo. CriadoEm é preservado; AtualizadoEm é atualizado em edição/ativação/desativação.

POST de especialidade já existente e DELETE de especialidade ausente retornam 204. POST valida a categoria ativa mesmo em repetição; categoria inativa retorna 409. DELETE continua permitido quando a categoria está inativa. A associação usa transação e bloqueio da linha da categoria, coordenando a validação de ativo com desativação concorrente; inserção usa ON CONFLICT na PK composta. Slug duplicado é tratado pelo índice único, inclusive em concorrência.

Exemplos PowerShell (token fornecido pelo emissor confiável):

```powershell
$base = 'http://localhost:5080'
$admin = @{ Authorization = "Bearer $env:CONECTA_ADMIN_TOKEN" }
$prestador = @{ Authorization = "Bearer $env:CONECTA_PRESTADOR_TOKEN" }
Invoke-RestMethod "$base/api/categorias"
Invoke-RestMethod "$base/api/categorias/reforma-e-reparos"
Invoke-RestMethod "$base/api/admin/categorias" -Headers $admin
$categoria = Invoke-RestMethod "$base/api/categorias" -Method Post -Headers $admin -ContentType application/json -Body '{"nome":"Reforma e reparos","slug":"reforma-e-reparos","descricao":"Reformas residenciais","iconeUrl":null}'
Invoke-RestMethod "$base/api/categorias/$($categoria.id)" -Method Put -Headers $admin -ContentType application/json -Body '{"nome":"Reformas","slug":"reforma-e-reparos","descricao":null,"iconeUrl":null}'
Invoke-RestMethod "$base/api/prestadores/me/categorias/$($categoria.id)" -Method Post -Headers $prestador
Invoke-RestMethod "$base/api/prestadores/me/categorias" -Headers $prestador
Invoke-RestMethod "$base/api/categorias/$($categoria.id)/ativo" -Method Patch -Headers $admin -ContentType application/json -Body '{"ativo":false}'
Invoke-RestMethod "$base/api/prestadores/me/categorias/$($categoria.id)" -Method Delete -Headers $prestador
```
