## Configuração local

Pré-requisitos: .NET SDK 10 e PostgreSQL 16. Execute na pasta `Conecta/apps/ConectaConstrucoes/backend`.

Configure variáveis da sessão PowerShell; substitua placeholders, sem salvar segredos em arquivos versionados:

```powershell
$env:ConnectionStrings__DefaultConnection = 'Host=127.0.0.1;Port=15432;Database=monorepo_db;Username=admin;Password=<senha-local>'
$env:Jwt__Issuer = '<emissor-acordado>'
$env:Jwt__Audience = '<audiencia-acordada>'
$env:Jwt__SigningKey = '<segredo-HS256-de-pelo-menos-32-bytes>'
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet restore Conecta.slnx
dotnet build Conecta.slnx --no-restore
```

`DefaultConnection` é a configuração canônica de main, usada igualmente por EF, Dapper e Evolve. O alias legado `ConnectionStrings__Conecta` é aceito somente quando DefaultConnection não está configurada. Alternativa: `dotnet user-secrets set 'ConnectionStrings:DefaultConnection' '<conexao>' --project Conecta.API` e equivalentes para Jwt:Issuer/Audience/SigningKey. Não há senha real em appsettings, .env.example ou defaults do Docker Compose. Configure também POSTGRES_PASSWORD e JWT_ISSUER/JWT_AUDIENCE/JWT_SIGNING_KEY no ambiente/.env local para usar Compose.

### Aplicar migrations / executar

```powershell
# Aplica somente Evolve; exige a conexão, mas não exige JWT e não inicia HTTP.
dotnet run --project Conecta.API --no-launch-profile -- --migrate-only
# A inicialização normal também aplica Evolve por padrão:
dotnet run --project Conecta.API --no-launch-profile --urls http://localhost:5080
```

Para ambientes onde as migrations são aplicadas separadamente, configure `Database__MigrateOnStartup=false`. Falhas na aplicação não são silenciadas: a API não inicia com schema incompatível. Evolve usa o schema selecionado por SearchPath, inclusive para changelog, e tem erase desabilitado.

Swagger em Development: `http://localhost:5080/swagger`; documento com Bearer: `/swagger/v1/swagger.json`; documento nativo: `/openapi/v1.json`. Clique Authorize e informe apenas o token. Em produção, publique por HTTPS; Swagger e documentos ficam disponíveis somente em Development.

### Porta local testada

Um PostgreSQL nativo do Windows ocupa 5432 neste ambiente; localhost:5432 pode atingir esse serviço em vez do container. Para acessar exclusivamente monorepo-postgres, usamos proxy temporário em 15432, sem alterar serviços, senhas ou volumes:

```powershell
docker run --rm -d --name con012-pg-proxy --network conecta_monorepo-network -p 127.0.0.1:15432:15432 node:20-alpine node -e "const net=require('net');net.createServer(c=>{const s=net.connect(5432,'monorepo-postgres');c.pipe(s).pipe(c);s.on('error',()=>c.destroy());c.on('error',()=>s.destroy());c.on('close',()=>s.destroy());}).listen(15432,'0.0.0.0');"
# Após encerrar as aplicações que dependem dele:
docker stop con012-pg-proxy
```

Se 5432 já apontar corretamente ao container, o proxy é desnecessário. Não reinicie/exclua serviços ou volumes para contornar o conflito.

## Schema e preservação dos dados

V1 cria o schema base; V2 preserva a evolução completa da equipe (RBAC, documentos, conversas, serviços, views e triggers). V3 adiciona AdicionadoEm, obrigatoriedade de ativo/datas, timestamptz para datas do módulo, descrição até 5000, check de slug, índice reutilizado de unicidade e FKs RESTRICT. A chave composta é mantida. Datas antigas das categorias são interpretadas como UTC na conversão. Timestamp sem fuso dos campos de suporte de Usuario permanece conforme V1/V2; EF converte explicitamente UTC para esse formato e vice-versa.

V1 estabelece `prestador_categorias.prestador_id -> prestadores(usuario_id)` e V3 mantém essa FK. V2 também contém `prestador` e `cliente` singulares para módulos novos; esta resolução não remove ou sincroniza automaticamente essas tabelas. O cadastro integrado às especialidades deve criar o registro em `prestadores` correspondente ao sub. Uma futura consolidação singular/plural exige migração coordenada pela equipe, não criação de prestadores fictícios.

V3 preserva IDs, nomes, descrições, estado ativo e vínculos existentes. Slugs inválidos e descrições maiores que 5000 precisam de revisão explícita antes da atualização: a migration falha, em vez de truncar dados ou normalizar possíveis colisões. V1/V2 não devem ser editadas após aplicação, nem seus checksums reparados automaticamente.

### Banco legado criado pelo CON_012 anterior com migrations EF

O public de monorepo_db usado em 04/10 foi criado pela migration EF anterior. Ele não possui todas as tabelas V1/V2. A presença de __EFMigrationsHistory bloqueia Evolve antes de alterar dados; essa proteção foi acrescentada para impedir execução concorrente de dois históricos.

Não apague o histórico EF, não marque V1 como aplicada sem completar seu schema e não execute V1 por cima de tabelas existentes. A adoção deve ser planejada com a equipe: faça backup, inventarie o schema/dados; prepare um novo schema com V1/V2/V3 usando SearchPath e `--migrate-only`; transfira os dados do módulo em transação, preservando IDs, timestamps e vínculos, e ajuste sequences; valide contagens/FKs e só então mude a conexão. Preserve o schema antigo até aprovar a conciliação. Esse procedimento não foi aplicado ao public nesta resolução: todos os testes usam schemas próprios descartáveis. A migração de dados legados é uma operação separada, não um efeito automático da inicialização.

## JWT e integrações pendentes

Autenticacao.API continua sem emissor/login integrado no ambiente inspecionado. Este módulo implementa a validação e define o contrato mínimo:

- HS256, segredo externo com pelo menos 32 bytes; assinatura e algoritmo validados.
- iss e aud exatos conforme configuração; exp obrigatório; tolerância de relógio de 30 segundos.
- Exatamente um sub inteiro positivo, correspondente a usuarios.id/prestadores.usuario_id.
- role com ADMIN ou PRESTADOR (múltiplas claims se necessário). Mapeamento automático de claims desabilitado.
- ADMIN_MASTER da modelagem V2 não vira ADMIN automaticamente: o emissor/equipe deve acordar a tradução explicitamente.

Headers arbitrários e prestadorId do cliente não selecionam o proprietário. Token PRESTADOR válido sem cadastro correspondente retorna 404. Consultas públicas e Swagger funcionam sem login; administração exige JWT ADMIN; especialidades exigem JWT PRESTADOR e registro real. Cadastro de usuários/prestadores e emissão de tokens pertencem às integrações pendentes, sem autenticação fictícia em produção.

## Endpoints e regras

| Método | Rota | Permissão | Sucesso |
|---|---|---|---|
| GET | /api/categorias | Público | 200, apenas ativas |
| GET | /api/categorias/{slug} | Público | 200, apenas ativa |
| GET | /api/admin/categorias | ADMIN | 200, inclui inativas |
| POST | /api/categorias | ADMIN | 201, Location e DTO |
| PUT | /api/categorias/{id} | ADMIN | 200, DTO |
| PATCH | /api/categorias/{id}/ativo | ADMIN | 200, DTO |
| GET | /api/prestadores/me/categorias | PRESTADOR | 200, próprias inclusive inativas |
| POST | /api/prestadores/me/categorias/{categoriaId} | PRESTADOR | 204 |
| DELETE | /api/prestadores/me/categorias/{categoriaId} | PRESTADOR | 204 |

400 entrada inválida; 401 token ausente/inválido; 403 perfil inadequado; 404 categoria/prestador ausente; 409 slug duplicado ou associação inativa. ProblemDetails não expõe mensagens do PostgreSQL.

Nome obrigatório até 100; slug até 100, aparado/minúsculo/sem acentos, espaços convertidos em hífens, formato `[a-z0-9]+(-[a-z0-9]+)*`; descrição opcional até 5000; ícone opcional até 255 com URL HTTP/HTTPS absoluta. AtualizadoEm muda em edição/ativação, CriadoEm é preservado.

POST repetido de especialidade ativa e DELETE de especialidade ausente retornam 204. POST de categoria inativa retorna 409; DELETE continua permitido após desativação. Associação bloqueia a linha da categoria em transação e usa ON CONFLICT na PK composta para coordenar concorrência.

```powershell
$base='http://localhost:5080'
$admin=@{ Authorization="Bearer $env:CONECTA_ADMIN_TOKEN" }
$prestador=@{ Authorization="Bearer $env:CONECTA_PRESTADOR_TOKEN" }
Invoke-RestMethod "$base/api/categorias"
$categoria=Invoke-RestMethod "$base/api/categorias" -Method Post -Headers $admin -ContentType application/json -Body '{"nome":"Reformas","slug":"reformas","descricao":null,"iconeUrl":null}'
Invoke-RestMethod "$base/api/categorias/reformas"
Invoke-RestMethod "$base/api/admin/categorias" -Headers $admin
Invoke-RestMethod "$base/api/categorias/$($categoria.id)" -Method Put -Headers $admin -ContentType application/json -Body '{"nome":"Reformas residenciais","slug":"reformas","descricao":null,"iconeUrl":null}'
Invoke-RestMethod "$base/api/prestadores/me/categorias/$($categoria.id)" -Method Post -Headers $prestador
Invoke-RestMethod "$base/api/prestadores/me/categorias" -Headers $prestador
Invoke-RestMethod "$base/api/categorias/$($categoria.id)/ativo" -Method Patch -Headers $admin -ContentType application/json -Body '{"ativo":false}'
Invoke-RestMethod "$base/api/prestadores/me/categorias/$($categoria.id)" -Method Delete -Headers $prestador
```
